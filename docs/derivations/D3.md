# D3 — Breaking ties by sequence number makes the simulation deterministic, and events are handled in timestamp order

**Author:** Aditya Singh (Architect) · **Roll no.** 250003007 · *draft prepared with Claude, declared in TOOLS.md*

**Assumptions** (all enforced by the code): the same parameters and seed; randomness only from
`eq::Rng` (mt19937_64 with our integer mapping) seeded with the given seed, drawn in program order
— during start-up (each flow's first transmission draws its loss and RTT) and inside handlers; integer
time with overflow checks; a correct queue (it satisfies INTERFACE.md); fixed start-up order (flow 0,
1, …, then the monitor); canonical output.

## (a) Determinism

Every insert gets seq = 0, 1, 2, … from one counter in the base class, so all keys (time, seq) are
distinct and the lexicographic order is a **strict total order**. Hence for any set P of pending events
"the minimum of P" is one specific event, and every correct `pop_min` returns it; a correct
`cancel(h)` returns true iff h is a pending key; `successor(t)` also has exactly one correct answer.
None of these depends on how the structure stores P.

Let the state after k dispatches be S_k = (now, P, flow handles, counters, RNG state, next seq,
hashes). Start-up is a fixed sequence of RNG draws and inserts that depends only on the parameters and the seed
(the RNG starts from the same seed, the flows are started in index order, and every insert gets the next
seq), so S_0 — including the RNG state after start-up — is the same in any two runs. Suppose two runs
agree on S_k. Both pop the same unique minimum; the handler for it is a deterministic function of
(S_k, event): it makes the same RNG draws, the same queue calls with the same results, and assigns the
same new seqs. So they agree on S_{k+1}. By induction they agree on every S_k, dispatch the same
events in the same order, give the same monitor answers, stop at the same k = E, and print the same
canonical output. ∎

*Without the tie-break* (key = time only), two events with equal time could come out in either order
depending on the heap's sift path or the tree's shape, and the outputs of A and B would differ. In the
default run 222 069 consecutive dispatches share a timestamp, so this is not hypothetical.

## (b) Timestamps never decrease

Let e_k be the k-th dispatched event, at time t_k. When e_k is popped it is the minimum of P_k, so every
pending event has time ≥ t_k. The handler inserts only at now + δ with δ ≥ 0 (δ ∈ {RTT, RTO, idle,
monitor}, all positive), and cancellations only remove events. So every event in P_{k+1} has time ≥ t_k,
hence t_{k+1} ≥ t_k. By induction t_1 ≤ t_2 ≤ …. Consequently no event is handled before an event with
a strictly smaller timestamp: if e_i came before e_j (i < j) then t_i ≤ t_j. ∎

This is a property of the simulation, not of the queue: the queue itself accepts inserts in the past.
The simulator also checks `time ≥ now` at run time and stops with exit code 3 if it ever fails.

## Where it is used

- `include/event_queue.h`, `EventQueue::insert` — assigns `seq = next_seq_` and increments it, so
  equal times are ordered by insertion (FIFO); `operator<(const Key&, const Key&)` — the total order on
  (time, seq) used by every structure.
- `include/rng.h`, `eq::Rng` — the only source of randomness, drawn in program order (assumption of (a)).
- `app/simulator.cpp`, `run` — the dispatch loop pops the minimum and checks `e.key.time >= now`
  ("time went backwards (D3 violated)", exit code 3), the run-time form of (b); every `now + delay` is
  overflow-checked in the `schedule` helper.
- `tests/test_sim.cpp` and `scripts/check_identical.sh` — identical output on heap, AVL and oracle, the
  golden checksum `0xcbd12e722cac3922`; REPORT.md §2.1.
